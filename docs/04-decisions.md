# 04 - Decisions

Each decision has a status, the reason, and when to revisit. Many of the *Rejected* items came from early agent pushback in 2025, so they are here to be questioned, not obeyed.

Statuses: **Accepted**, **Rejected**, **Reopened** (under discussion), **Parked** (later), **Superseded**.

## Technical

| ID | Decision | Status | Why / when to revisit |
| --- | --- | --- | --- |
| D-01 | Rebuild in Rust, replacing Electron + React + TypeScript | Accepted | Speed and a safe core. The old stack had unmaintained parts (Create React App, mmap-io, fluent-ffmpeg) and constant native-rebuild trouble. |
| D-02 | Memory-map **local** files only | Accepted | Mapping network files can crash on disconnect and is slow. Compressed files are decoded straight from the network in one pass. Uncompressed files on a network drive are copied to local temp first, then mapped. See the table in 03-architecture. |
| D-03 | Decode once, work from memory, cache measurements | Accepted, with a caveat | The old "mmap for preview" never fed FFmpeg, so it did not help. First measurement (Houses of the Holy, 41 min FLAC on the NAS, 8 tracks): one pass with 8 meters took 5.7 s, against 9.2 s for 8 separate FFmpeg runs and 7.8 s for one FFmpeg pass. That is about 1.6x faster, not the dramatic win first expected, because FFmpeg also seeks and does not re-decode the whole file per track. The bigger saving should come in the full run, where analysis and export share one decode. Reading the file alone takes 2.4 s of the 5.7 s. |
| D-04 | The "Range" column shows LRA (loudness range) | Accepted | Decided 2026-10-23. The mockup header says "(DR)" and its whole-number values resemble TT DR Meter scores, which was only an example of the layout. The old code already fed LRA into that column. The column is labelled **Range (LRA)** and shows LU. True DR (the TT DR Meter style score) is out of scope and can be added later if wanted. Open, low priority: our LRA differs from FFmpeg's by up to 0.4 LU on some tracks (No Quarter: 20.10 against 19.7) while loudness and true peak match. Gain planning does not use LRA, so this only affects the display. If it ever matters, settle it with the EBU Tech 3341/3342 test signals, which come with specified expected values, instead of comparing tools. |
| D-05 | Gain method: linear gain capped by peak protection | Accepted | Keeps dynamics (the "lossless sweetener" idea). The old plan used `loudnorm`, which can change dynamics. Revisit if clip-limiting is wanted. |
| D-06 | Keep FFmpeg for encoding and awkward inputs | Accepted | Mature ALAC/AAC encoders. Fed PCM on stdin, so no double decode. |
| D-07 | UI: terminal view first, Tauri desktop app later | Accepted | Data-heavy flow suits a table. Both sit on the same core. |
| D-09 | Decoder: Symphonia, with FFmpeg only for formats it cannot read | Accepted | Measured with files on a local disk and nothing else running, for the 41-minute album: Symphonia decodes FLAC in 1.4 s and ALAC in 4.3 s, against FFmpeg's 0.5 s and 1.0 s. FFmpeg is faster, but decoding is never the slow part: just reading the file off the NAS takes about 3 s at 80 MB/s, and a whole export takes about 9 s. Switching would save 1 to 3 s per album. Symphonia matched FFmpeg's loudness and peak on every track. Revisit only if profiling shows decoding on the critical path (for example big multichannel or DSD files, Phase 6). The earlier 21.8 s ALAC figure was a cold first read of that file from the NAS (18.6 s cold, 4.2 s on the next read), not the decoder. |
| D-10 | Overlap reading and decoding | Parked | Reading and decoding currently take turns. A read-ahead thread could hide most of the network read on a NAS, and cold first reads from the NAS vary a lot (the album ALAC took 18.6 s cold and 4.2 s warm). Larger read blocks made no difference in a test. Do it once the whole pipeline is measured. |
| D-11 | The cache recognises a file by content, not name or date | Accepted | Key is the file size plus a hash of three 64 KiB slices. It survives renames, copies and moves, which the app's own File Strategy and the NAS both cause. Cost: three small reads per file. Known trade-off: editing the tags changes the first slice, so a re-tagged file is measured again. Results are stored per CUE layout (in CD frames, so independent of sample rate), and a version number discards old entries when the measuring code changes. Measured on Houses of the Holy: 5.3 s cold, 0.00 s cached. |
| D-12 | Gain only. The true-peak ceiling is the hard limit on how far the volume knob can turn. | Accepted | Decided 2026-10-24. The tool never compresses or limits the waveform, so no peak data is ever lost. The ceiling decides how much gain a song can take, and a song that runs out of headroom stays below the target and is marked `*`. Seen on Houses of the Holy at -16 LUFS with a -0.6 dBTP ceiling: The Rain Song wants +4.66 dB but can only take +1.31 dB. Someone who asks for -10 LUFS with a 0 dBTP ceiling will get a wide spread of volumes, and that is the setting working as intended, not a flaw. Any waveform compression is an optional extra for much later, after everything else works. For that day: a light limiter measured on this album reached the target within 0.1 LU and moved the loudness range by under 0.2 LU, but FFmpeg's `alimiter` works on sample peaks, so it needed to be set about 1.4 dB below the true-peak ceiling to stay under it. A listening comparison is in `testdata/ab-limiter/`. |
| D-13 | Nothing original is touched until everything has been written | Accepted | Every song is encoded to a temporary file, and files are only moved into place once the whole source has decoded and every encode has succeeded. A failure deletes the temporary files and leaves originals as they were. Tested, including a failed placement. |
| D-14 | File Strategy meanings | Accepted, reshaped by D-21 (the four choices below are now three separate ones; numbering only happens on a clash) | Serialize always adds the suffix. Rename-old renames an existing file at the same path and never overwrites an earlier backup. Replace overwrites only a file at exactly the same path and never deletes a differently named source. Save-to writes elsewhere and serializes clashes. Replace needs an explicit `--yes` on the command line. For a CUE album, which has no same-named output to replace, Replace writes the songs next to the image and keeps the image (decided 2026-10-24). Replace is expected to become the default strategy once it has proven itself, and until then the safer choices stay the default. Planned: after a run that has been verified, offer to move the CUE image (or a replaced source) to the Recycle Bin or Trash, always with explicit confirmation. Rule for testing it: the real action sits behind a small interface with a fake for tests, and tests only ever use generated files or copies in temporary folders, never `testdata/` originals or the real Recycle Bin. |
| D-15 | Dither only when needed | Accepted | A gain on 16-bit audio, or a drop from 24 to 16 bits, uses triangular dither. Audio at 0 dB is never dithered, so it stays bit-exact, and 24-bit output is not dithered. |
| D-16 | FFmpeg is found via `RANGEFORGE_FFMPEG`, next to the program, on the path, or in the usual package folders | Accepted for now | A window opened from Finder or the Start menu does not get a terminal's path, so on a Mac the Homebrew folder (`/opt/homebrew/bin`) would be missed. It now looks there and in `/usr/local/bin` too, and next to the program, so an `ffmpeg` file dropped beside the app is found. Found on the first Mac test (2026-10-24). Bundling one per platform is Phase 8. FFmpeg is also started without a console window on Windows. |
| D-17 | Peaks above 0 dBFS, and hitting a LUFS target without losing peak data | Parked, to discuss together with any compression | Raised 2026-10-24: the user has seen digital peaks over 0 in a real file, and other people's files and habits will be messier than their own. When compression comes up, the same conversation must cover ways to reach a loudness target while preserving peaks, and what to do with "overs". Three different cases: inter-sample overs (all stored samples at or below 0 dBFS, but the waveform between them goes higher, which true peak measures), float files (can store samples above 0 dBFS), and already-clipped files (flat tops, so the data is gone). Today the planner already handles the first two without losing data, because a file whose true peak is above the ceiling gets a negative gain until it fits, and the decoder keeps values above 1.0. Gaps to close: a float output option (32-bit float WAV is the only common container that can hold overs, ALAC and FLAC cannot), a warning when peak protection is off and a gain would clip on the way out, and a tool-side flag for files that arrive already clipped. Tests to add then: a float WAV with samples above 1.0 measured and exported. |
| D-18 | Presets store output and volume, not the File Strategy; saved in a small JSON file | Accepted | A preset holds codec, bit depth, target loudness, peak protection and ceiling. The File Strategy is about what is on disk right now and not about the sound, so it is not part of a preset. Presets live in `presets.json` in the settings folder and the five from the mockup are built in (the mockup's stray "(1)" and "(test)" are dropped from their names). Save is only on offer when the settings differ from the selected preset, as in the mockup. A file that cannot be read is set aside as `presets.json.bad`, never silently overwritten. Sample rate and channels are not part of a preset yet because they cannot be set yet. The *current* output format and volume are also remembered between sessions in `settings.json` (separately from presets), and the matching preset is highlighted again when they equal one. |
| D-19 | The app starts on "next to the original, add a number if taken", not the mockup's Replace | Accepted for now | Overwriting and deleting stay opt-in, each with a confirmation, until they have proven themselves (D-14, D-21). Numbering never touches an existing file. |
| D-30 | Files of one album gather under a heading, as a display only | Accepted | Decided 2026-11-08. Dropping a folder of loose songs made two rows per song. Single files that are scanned and identified, with the same album, artist and folder (case and spacing ignored), are drawn under one heading that selects, edits, tags and includes them together and can be folded. The **folder** is part of the key so a `2ch` and a `6ch` copy of one album never merge. The files stay separate jobs underneath: output naming (single versus album pattern), folders and the run are unchanged, which avoids reworking planning for a convenience. Only files with an album name group, and a file regroups as soon as its names are edited. **Revisit:** real grouping (one job for many files) only if the single-file naming pattern gets in the way. |
| D-29 | Names and tags can be edited by hand; one action works on a selection; Last.fm can be asked on demand | Accepted | Decided 2026-11-08. Closes D-25 step 4 and the planned tag editing. **Names:** typed names become an identity source ("hand") that no scan replaces; Last.fm, file names and written tags all use them. **Tags:** each song keeps tags added and removed by hand. A removed tag stays removed after Last.fm is asked again; removing every tag writes an empty genre rather than keeping the old one. **Selection:** click, Ctrl and Shift pick songs, and one right-click acts on all of them, with empty name fields keeping what each song has. **On demand:** right-click Get tags from Last.fm asks afresh even while automatic lookups are off (a key and the Metadata switch are still needed), and Settings can clear the saved answers. Every lookup is logged with the names sent and each tag's score. Song-level genres now allow up to four from 5 hits (first two from 40, then 15; the cut is 5 for albums too): a rarer but distinct tag such as reggae on D'yer Mak'er should show. Edits live only for the session; remembering them between sessions is not built. |
| D-28 | DSD is read through FFmpeg, measured at a fixed 88.2 kHz, and written with its own fallback format; File Strategy and the confirmation are remembered | Accepted | Decided 2026-11-07. `.dsf` and `.dff` are decoded by FFmpeg (Symphonia cannot) to float audio with every channel kept. Measuring always uses 88.2 kHz, so a saved measurement never depends on what the file is later written as. Export decodes straight at the target rate. The main Output Format wins wherever it names a value; the DSD Format (sample rate 88.2 kHz and bit depth 24 by default, optional codec and container) fills in only "original" and "source". The File Strategy, the DSD Format and the "ask before overwriting or deleting" switch are kept in `settings.json`; "don't ask again" is the user's choice and Settings can undo it (this softens D-14 for people who ask for it: the defaults still ask). |
| D-27 | Output format: codec, container (native or mka), sample rate and bit depth; channels stay original | Accepted | Decided 2026-10-25. Sample rates: Original, 44.1, 48, 88.2, 96, 176.4, 192 kHz (AAC only up to 96 kHz). Matroska audio (.mka) is offered for every codec. Presets (D-18) now remember container and sample rate. DSD needs its own fallbacks for all three "original" values (next step). |
| D-26 | Genres: from Last.fm, written comma separated with Radio last | Accepted | Decided 2026-10-25. A song's genres are, in order: what its file or CUE sheet already says, up to three Last.fm album genres (plain), up to four song-level extras that are not the album's (pink; was two, see D-29), and Radio if it charted (Radio is just another genre, last, for quick scanning). They are written into the file's genre tag as one comma separated value when Run is pressed; with Metadata off nothing is shown or changed. Last.fm tags are filtered by a list of non-genres (opinions, habits, nationalities, decades, the artist's own name, matched as whole words), a popularity cutoff (5 hits for both albums and songs, set 2026-11-08 from real counts: real genres such as dream pop score 8, list-style and year tags 1 or 2; the first usable tag is always kept) and capitals (`classic rock` becomes `Classic Rock`). A single file waits to be asked about until its tags have been read, so a guess from its file name is not wasted on a question. Answers are cached on disk (90 days; 14 days for "no tags"); the key is only ever sent to Last.fm and never appears in a log, an error, or the window. **Planned:** × on chips and Add tag / Rescan tags on a selection (D-25). |
| D-31 | Song-level tags come from the song's Last.fm tags page, which a person reads and adds with Add a tag | Accepted | Decided 2026-11-08, changed twice the same day. The API's `track.getTopTags` and `track.getInfo` answer with nothing for songs whose tags show on the site (D'yer Mak'er, Shot at the Night), while `album.getTopTags` works. The tags page (`last.fm/music/<artist>/_/<song>/+tags`) does hold them, and they differ from the album's in the way that matters: D'yer Mak'er lists *reggae* third, and Shot at the Night lists *synthpop* first where the album has it at 1 hit. But the page sits behind a JavaScript bot check ("Client Challenge"), so a plain HTTP request gets no tags: reading the page for the user was built first and never worked live. **Now:** right-click a song, **Open song tags page on Last.fm** opens the page in the user's own browser (up to 6 tabs for several songs), and the tags are added with the ordinary **Add a tag…** box, which takes several tags separated by commas, semicolons or line breaks, so a list copied from the page can be pasted as it is. They are green tags, kept for the session like any hand-added tag. A second route was built for a day (a separate "Paste song tags…" box that saved to its own file and showed pink song tags) and removed, because it did the same job as Add a tag with a second dialog to learn. Songs are no longer asked of the API at all; albums keep using it. The program never fetches the tags page itself. Revisit if Last.fm opens song tags in its API, or if saving hand-added tags between sessions is wanted (see D-32). |
| D-32 | Other sources for song-level tags | Rejected | Tried 2026-11-08 on D'yer Mak'er and Shot at the Night. **MusicBrainz:** the recording lookup returns no tags, the same empty answer as Last.fm's API; its album (release group) tags are real and curated but thin (Direct Hits has 5 votes for its top tag). **Wikidata** (`genre` on the song item): coarse and inconsistent. D'yer Mak'er has only *rock music*, no reggae; Mr. Brightside's song and recording items have no genre at all; a curly apostrophe or a different capital (Outkast, OutKast) misses; Paranoid Android found nothing; it also rate-limits to about one request a minute after a few. **Discogs:** genres sit on the release, not the song. **Spotify:** song-level data is gone for new apps. **A hidden browser window (the app is Tauri) to pass the bot check:** not done, because it works around a check Last.fm put there on purpose, and Last.fm's terms probably frown on automated page reads. **Analysing the audio** (for example Essentia genre models) is the one option that could hear reggae in D'yer Mak'er with no network at all: parked as an idea, not built. |
| D-25 | Who a song is: tags, then the CUE sheet, then a guess from the file name, then by hand | Accepted (the last step is planned) | Decided 2026-10-25. Lookups and `{artist}`-style names need an artist and a title, and not every file has them. Each song carries an identity with its source. CUE songs take it from the sheet. A single file is first guessed from its name and folders, which costs nothing and shows at once; when its measurement finishes, the tags read from the start of the file replace the guess where they have something to say, and the guess only fills gaps. The guess understands `Artist - Title`, a leading track number (`07 - `, `07. `, `7-`, `07 `), `03 - Artist - Title`, album folders such as `Artist - Album (1973) [FLAC]` and `1973. Album`, and the folder above as the artist unless it is a generic name (Music, Downloads, ...). A bare number counts as a track only with a separator or a leading zero, so `99 Luftballons` stays whole. Read back tags were checked against FLAC and ALAC files our own export writes. Single-file name patterns can now use every variable. A song with no artist or title is simply not looked up. Step 4, correcting an identity by hand, comes next. **Tag editing, planned:** chips with a small × to remove an unwanted tag before it is written (staying removed on rescans), and, on one or many selected songs or albums, a right-click **Add tag…** and **Rescan tags**. This assumes tags are written into the files, which is not built yet; where Radio is written (ALAC holds one genre string, FLAC several) is still open. |
| D-24 | The Radio tag, and how API keys are kept | Accepted | Decided 2026-10-25. **Radio:** a song is Radio if it appears anywhere in the Hot 100 history. The 42 MB `all.json` is reduced once to a 2 MB local index of the 32,763 songs that charted (artist, title, best position, first year), and refreshed with a conditional request (`ETag`), so the big file is only downloaded when it changed; checks are at most 12 hours apart, and a failed check keeps the copy on disk. Matching compares normalised text: no case, accents, apostrophes or leading "The", `&` as `and`, bracketed notes and trailing version notes (`Remastered`, `Live`) dropped, and a lead artist matches when the chart credits guests (`Featuring`, `with`). It also finds `Simon and Garfunkel` for `Simon & Garfunkel`. Checked against the real file: D'yer Mak'er #20, Over the Hills and Far Away #51 and Living Loving Maid #65 match, and The Rain Song, No Quarter, The Ocean and The Crunge do not. A song is looked up by its identity (D-25), whether it came from a CUE sheet, a file's tags or a file name. **Keys:** kept in the operating system's credential store, not in `settings.json`; the window is only ever told whether a key exists. `LASTFM_API` in the environment (or a `.env` file, in debug builds only) is a fallback for development, and a saved key wins over it. Each key has its own enable checkbox, and everything also needs the main Metadata API switch. All switches start off. |
| D-23 | Installers: MSI and DMG, FFmpeg inside, unsigned for now, no command-line tool | Accepted | Decided 2026-10-25. Tauri's bundler makes the Windows MSI and the macOS `.app` in a DMG; a Release workflow builds them (D-08's platforms), by hand or on a version tag. FFmpeg is bundled as a sidecar so there is nothing to install: an LGPL build only (no GPL or non-free parts), which is enough because only FFmpeg's own ALAC, FLAC, AAC and PCM encoders are used. macOS and Linux builds come from the pinned source tag with no outside libraries; Windows uses BtbN's prebuilt LGPL build (about 160 MB packed, so the MSI is large; a smaller custom build is possible later). Licence text and source location are in `THIRD_PARTY_NOTICES.md`. Not signed: Windows shows SmartScreen and macOS needs right-click then Open (the app is ad-hoc signed because Apple Silicon requires some signature); revisit when others will use it. The command-line program is not shipped: without drag and drop it is not usable in practice, and it stays as a developer tool. Supersedes the "Bundling is Phase 8" note in D-16. |
| D-22 | Metadata comes in a deliberate order, starting with file name patterns | Accepted | Decided 2026-10-25. Order: (1) file name patterns with variables, which need no network or keys (built); (2) the Radio tag from the Hot 100 file, a local lookup with a small index built once from the 42 MB download; (3) Last.fm genres, which need a key (the old one leaked into git history and should be rotated) and a filter, since Last.fm tags include things like "seen live"; (4) Discogs is parked (S-10). Patterns apply to the file name only, not folders, and single files may only use `{name}`. Still open: whether Radio and genre are only shown in the Tags column or also written into the files (ALAC takes one genre value, FLAC several), how many genres per song, and album-level versus song-level. Lookups will be cached by artist and album and never run while measuring. |
| D-21 | File Strategy is split in three, and the window follows the first real use | Accepted | Decided 2026-10-24 after trying the window on Windows and a Mac. (1) Where files go (next to the original, a subfolder of it, or one folder) is separate from what happens when a name is taken (add a number, rename the existing file, overwrite) and from deleting the original afterwards. A name changes only on a clash, so with a CUE album, whose songs have new names, nothing is renamed. This replaces the four-way choice in D-14. (2) Delete original is opt-in, asks first, and never runs if a song was left out. (3) Songs can be left out of a run with a tick box or a right-click, and finished albums can be cleared from the list. (4) The teal colour scheme goes. The window follows the system's light or dark setting, and only the first and last columns resize. (5) Dropping an audio file finds the CUE sheet beside it. Still to do from the same review: export file naming and where it lives, a Settings window, tags filling the wide last column, and column resizing. |
| D-20 | Keep the app's own data from growing without limit | Parked | Two things grow: the measurements cache (one small file per audio file, about 1.6 KB per album, so 100,000 files is roughly 160 MB, fine for now) and the on-screen log, which keeps every line for the whole session. When it matters: cap the log to the most recent lines, and prune the cache to the newest N entries, dropping any from an older measuring version. Raised 2026-10-24. |
| D-08 | Platforms: Win x64, macOS ARM first; macOS Intel, Linux GNU, Win ARM follow | Accepted | One CI matrix builds all. Only the first two are tested on real hardware. |

## Naming and wording

- The button says **Run**, not "GO" or "Make It So". Movie references explain ideas and are not UI text.
- The UI uses technical terms (LUFS, dBTP) because it is an expert layout. The old "never say LUFS" rule applied to a market-facing design that is on hold.
